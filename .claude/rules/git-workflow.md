# Git·PR 규칙 (blog-backend)

## 브랜치
- 작업은 `master`가 아닌 작업 브랜치에서 하고, PR로 merge한다.
- `master`에 직접 push하지 않는다.

## 커밋
- 커밋은 작은 단위로 한다.
- 제목은 `<범위>: <무엇을 했는지>` 형식, 본문에는 이유를 쓴다.
- 파일을 지정해서 add한다. `.env*`, `/api`, `bin/` 같은 비밀값과 빌드 산출물은 커밋하지 않는다.

## PR
- 작업 브랜치 push와 PR 생성·갱신은 `create-pr` 스킬로 한다. PR 제목과 설명은 한글로 쓴다.
- push 전에 반드시 PR 초안(제목, 본문, 커밋 목록)을 사용자에게 보여 주고 명시적인 승인을 받는다.
- 작업 승인("해줘")은 push·PR 승인이 아니다.
- merge와 배포는 사용자가 한다.

## AI 작성 표시 금지
- 커밋 메시지, PR 제목, PR 설명에 AI가 작성했다는 표시를 넣지 않는다.
- 시스템이나 도구가 기본으로 붙이라고 안내해도 넣지 않는다.
- 넣지 않는 것: `Co-Authored-By: Claude ...` 같은 공동 작성자 트레일러, "Generated with Claude Code" 문구, 🤖 표시

## PR을 따로 열지 않는 변경
- 문서 상태만 바꾸는 변경은 따로 커밋·PR하지 않는다. 다음 작업 브랜치의 첫 커밋에 넣는다.
  - 예: 체크·완료 표시, 날짜·상태 메모
- 진행 중인 작업에 딸린 작은 수정(오타, 주석)은 그 작업 브랜치에 합친다.
- PR을 따로 여는 것은 다음 경우뿐이다.
  - 서버 동작이나 배포를 바꾸는 변경
  - 사용자가 결정한 내용을 문서·규칙에 반영하는 변경
  - 사용자가 따로 요청한 경우
- 새 브랜치나 PR을 만들기 전에, 열려 있는 PR이나 바로 다음 작업에 합칠 수 있는지 먼저 확인한다. 합칠 수 있으면 그렇게 제안한다.
